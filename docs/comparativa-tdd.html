🎯 Filosofía común del TDD

Antes de mostrar las diferencias de sintaxis entre lenguajes, es fundamental establecer los conceptos que comparten todas las tecnologías empleadas en el proyecto. Estos fundamentos son transversales a Java, Kotlin, Python, React y Angular.

1. El ciclo Red → Green → Refactor

🔴 Red

Se escribe primero el test que describe el comportamiento esperado. Al ejecutarlo, debe fallar, porque el código de producción aún no existe. Esta falla intencional confirma que el test realmente detecta la ausencia del código.

🟢 Green

Se escribe el mínimo código necesario para que el test pase. No se anticipan funcionalidades futuras ni se agregan validaciones extra: solo lo justo para pasar del rojo al verde.

🔵 Refactor

Con el test en verde, se mejora el código de producción (nombres, eliminación de duplicación, extracción de métodos, legibilidad) sin cambiar su comportamiento. La suite de tests actúa como red de seguridad: si un refactor rompe algo, un test se pondrá en rojo y avisará de inmediato.

2. Estructura AAA (Arrange - Act - Assert)

Todos los tests, sin importar el lenguaje, siguen esta estructura de tres fases:

  • Arrange: preparar los datos, instanciar objetos y configurar el estado inicial necesario.
  • Act: ejecutar la acción concreta que se quiere probar (típicamente una llamada a un método).
  • Assert: verificar que el resultado obtenido coincide con el resultado esperado.

3. Principio FIRST

Fast

Los tests deben ejecutarse rápido para poder correrlos frecuentemente durante el desarrollo.

Isolated

Cada test es independiente de los demás. El orden de ejecución no debe afectar el resultado.

Repeatable

Debe producir el mismo resultado en cualquier entorno, sin depender de red, hora o estado externo.

Self-validating

El test decide por sí mismo si pasó o falló mediante aserciones automáticas.

Timely

Se escribe junto (o antes) del código de producción, no como un agregado posterior.

4. Tipos de pruebas

Tipo Qué prueba Cuándo se usa
Unitaria Una clase o función aislada, sin dependencias externas. Base de la pirámide de pruebas. La más común y rápida.
Integración Dos o más componentes reales trabajando juntos. Para verificar que los componentes interactúan correctamente.
Unitaria con mocks Una clase aislando sus dependencias mediante dobles (mocks, stubs). Cuando la dependencia es lenta, costosa o incontrolable.

Java Punto 1 — TDD con JUnit 5

Responsable: Carlos Alberto Díaz · Framework: JUnit Jupiter 5.10.2 · Build: Maven 3 · JDK: Temurin 17

Descripción del ejercicio

Se implementó una clase Calculator con los métodos add, subtract, multiply y divide. Cada método se desarrolló aplicando el ciclo Red → Green → Refactor: primero se escribió un test que llamaba al método (fallando en compilación), luego se creó el método con la implementación mínima necesaria, y finalmente se verificó que el test pasara en verde.

Código del test Código real del proyecto

package com.example;

import static org.junit.jupiter.api.Assertions.assertEquals;
import org.junit.jupiter.api.Test;
import com.example.util.Calculator;

class CalculatorTest {

    private final Calculator calculator = new Calculator();

    @Test
    void addition() {
        assertEquals(2, calculator.add(1, 1));
    }

    @Test
    void subtraction() {
        assertEquals(3, calculator.subtract(5, 2));
    }

    @Test
    void multiplication() {
        assertEquals(12, calculator.multiply(3, 4));
    }

    @Test
    void division() {
        assertEquals(5, calculator.divide(10, 2));
    }
}

Código de producción Código real del proyecto

package com.example.util;

public class Calculator {

    public int add(int a, int b) {
        return a + b;
    }

    public int subtract(int a, int b) {
        return a - b;
    }

    public int multiply(int a, int b) {
        return a * b;
    }

    public int divide(int a, int b) {
        return a / b;
    }
}

Elementos técnicos aplicados

  • La anotación @Test de JUnit Jupiter identifica cada método como una prueba automatizada.
  • La aserción assertEquals(esperado, obtenido) es autovalidante: el test decide por sí mismo si pasa o falla.
  • Separación estándar de paquetes según convención Maven: com.example.util para producción en src/main/java, com.example para tests en src/test/java.
  • Cada test es independiente: se instancia una nueva Calculator por clase, cumpliendo el principio Isolated del FIRST.
✅ Resultado: 5 tests ejecutados, 0 fallos, 0 errores (mvn test)

package dev.orlan.test.qa.c01_annotations

import dev.orlan.test.qa.entity.Calculator
import org.junit.jupiter.api.Assertions.assertEquals
import org.junit.jupiter.api.Test

class CalculatorTests {

        val result = calc.multiply(2, 3)
        assertEquals(6, result)

        val result = calc.divide(10, 2)
        assertEquals(5, result)

  • Estructura AAA implícita en cada test: instancia de Calculator (Arrange), llamada al método (Act), assertEquals (Assert).

Softtek Punto 2 — Ejercicios JUnit + Mockito

Responsable: Carlos Alberto Díaz · Framework: JUnit 5 + Mockito 5.11 · Build: Maven

Descripción del ejercicio

Replicación modernizada del ejercicio propuesto por Softtek en su artículo "¿Por qué hacer testing unitario?". Consiste en un solucionador de ecuaciones de primer grado del tipo ax + b = c, con la solución x = (c - b) / a. El proyecto contiene dos clases de producción y tres suites de pruebas que ilustran los tres tipos principales de test.

Estructura del proyecto

Suite Tipo Qué prueba
ParseadorTest Unitaria pura Los métodos del Parseador, sin dependencias externas.
EcuacionPrimerGradoIntegrationTest Integración EcuacionPrimerGrado usando el Parseador real.
EcuacionPrimerGradoMockitoTest Unitaria con mocks Solo la fórmula, con Parseador mockeado.

Ejemplo destacado: test con Mockito Código real del proyecto

@ExtendWith(MockitoExtension.class)
class EcuacionPrimerGradoMockitoTest {

    @InjectMocks
    private EcuacionPrimerGrado ecuacionPrimerGrado;

    @Mock
    private Parseador parseador;

    @Test
    void solucionaEcuacionConMenos() {
        // Arrange: configuramos el mock
        String ecuacion = "2x - 1 = 0";
        when(parseador.obtenerParte1(ecuacion)).thenReturn(2);
        when(parseador.obtenerParte2(ecuacion)).thenReturn(-1);
        when(parseador.obtenerParte3(ecuacion)).thenReturn(0);

        // Act
        Double resultado = ecuacionPrimerGrado.obtenerResultado(ecuacion);

        // Assert
        assertEquals(0.5, resultado);
    }
}

Elementos técnicos aplicados

  • @ExtendWith(MockitoExtension.class) integra Mockito con JUnit 5, reemplazando el MockitoAnnotations.initMocks() del ejemplo original en JUnit 4.
  • @InjectMocks permite que Mockito inyecte automáticamente los mocks en la clase bajo prueba.
  • @Mock crea un doble del Parseador cuyo comportamiento se define con when(...).thenReturn(...).
  • Al aislar el SUT (System Under Test), los tests unitarios verifican únicamente la fórmula matemática, sin depender de la lógica de parseo de strings.
  • Los comentarios en el test señalan explícitamente las tres fases de la estructura AAA (Arrange, Act, Assert).
✅ Resultado: 12 tests ejecutados, 0 fallos, 0 errores (mvn test)

Python Punto 3 — CRUD Flask + pytest

Responsable: Jorge Rivera · Framework: Flask + SQLite + pytest · Build: pip

Descripción del ejercicio

CRUD web REST desarrollado en Python con Flask como framework web y SQLite como base de datos. La API expone endpoints para gestionar estudiantes y libros con las operaciones CRUD completas. Los tests se implementaron con pytest siguiendo TDD, cubriendo tanto los casos exitosos como los edge cases (datos inválidos, recursos inexistentes).

Endpoints implementados

Rutas REST

  • GET /estudiantes — listar
  • GET /estudiantes/<id> — obtener
  • POST /estudiantes — crear
  • PUT /estudiantes/<id> — actualizar
  • DELETE /estudiantes/<id> — eliminar
  • Rutas equivalentes para libros

Aislamiento de tests

  • BD SQLite en archivo temporal (tmp_path)
  • Nueva instancia de app por test
  • Cliente de pruebas de Flask (test_client)
  • Fixtures encadenados para setup común

Código del test Código real del proyecto — test_estudiantes.py

import pytest
from app import app as flask_app


@pytest.fixture
def app(tmp_path, monkeypatch):
    db_file = tmp_path / "test.db"
    monkeypatch.setenv("DATABASE", str(db_file))
    flask_app.config.update(TESTING=True)
    return flask_app


@pytest.fixture
def client(app):
    return app.test_client()


@pytest.fixture
def estudiante_creado(client):
    return client.post(
        "/estudiantes",
        json={"nombre": "Ana", "email": "ana@test.com", "edad": 20},
    ).get_json()


def test_crear_estudiante(client):
    response = client.post(
        "/estudiantes",
        json={"nombre": "Juan", "email": "juan@test.com", "edad": 22},
    )
    assert response.status_code == 201
    data = response.get_json()
    assert data["nombre"] == "Juan"
    assert "id" in data


def test_crear_estudiante_datos_invalidos(client):
    response = client.post("/estudiantes", json={"nombre": "Sin email"})
    assert response.status_code == 400


def test_listar_estudiantes(client, estudiante_creado):
    response = client.get("/estudiantes")
    assert response.status_code == 200
    assert len(response.get_json()) == 1


def test_obtener_estudiante_existente(client, estudiante_creado):
    response = client.get(f"/estudiantes/{estudiante_creado['id']}")
    assert response.status_code == 200
    assert response.get_json()["nombre"] == "Ana"


def test_obtener_estudiante_inexistente(client):
    response = client.get("/estudiantes/999")
    assert response.status_code == 404


def test_eliminar_estudiante(client, estudiante_creado):
    response = client.delete(f"/estudiantes/{estudiante_creado['id']}")
    assert response.status_code == 200

Elementos técnicos aplicados

  • Fixtures encadenados: client depende de app, y estudiante_creado depende de client. pytest resuelve la cadena automáticamente.
  • Aislamiento por test: tmp_path crea una carpeta temporal única para cada test, garantizando una BD SQLite limpia (principio Isolated).
  • monkeypatch.setenv: altera variables de entorno solo durante el test, restaurándolas al finalizar.
  • Cliente de prueba de Flask (app.test_client()) permite simular peticiones HTTP sin levantar un servidor real, respetando el principio Fast.
  • Edge cases explícitos: tests como "datos inválidos" (400) e "inexistente" (404) verifican que la API responde correctamente a errores, no solo al camino feliz.
  • Aserciones nativas de Python: assert x == y reemplaza a assertEquals. pytest reformatea automáticamente los errores para hacerlos expresivos.
✅ Resultado: 6 tests para estudiantes + 6 para libros ejecutados en verde (pytest passed)

Los tests cubren tanto casos unitarios por componente como escenarios end-to-end de integración.

Componentes implementados

Estructura

  • ListTarea — lista con estado vacío
  • TareaItem — ítem individual editable
  • App — componente raíz que integra todo

Niveles de prueba

  • Unitarios por componente
  • Integración end-to-end del CRUD

Código del test Código real del proyecto — App.test.tsx

import { render, screen } from "@testing-library/react"
import userEvent from "@testing-library/user-event"
import App from "../App"

describe('Prueba end to end - integracion del CRUD', () => {
    beforeEach(() => {
        localStorage.clear()
    })

    it('agrega, marca como completada y elimina una tarea', async () => {
        const user = userEvent.setup()
        render(<App />)

        // Agregar
        const input = screen.getByLabelText(/nueva tarea/i)
        await user.type(input, 'Estudiar TDD')
        await user.click(screen.getByRole('button', { name: /agregar/i }))

        expect(screen.getByText('Estudiar TDD')).toBeInTheDocument()

        // Marcar como completada
        const checkbox = screen.getByRole('checkbox', { name: /estudiar tdd/i })
        await user.click(checkbox)
        expect(checkbox).toBeChecked()

        // Eliminar
        await user.click(
            screen.getByRole('button', { name: /eliminar estudiar tdd/i })
        )
        expect(screen.queryByText('Estudiar TDD')).not.toBeInTheDocument()
    })

    it('no permite agregar una tarea con input vacio', async () => {
        const user = userEvent.setup()
        render(<App />)

        await user.click(screen.getByRole('button', { name: /agregar/i }))

        expect(screen.getByText(/no hay tareas/i)).toBeInTheDocument()
    })
})

Elementos técnicos aplicados

  • @testing-library/user-event: simula interacciones más realistas que fireEvent — teclea carácter por carácter, respeta focus, hover y otros comportamientos del navegador.
  • Consultas por accesibilidad: getByLabelText, getByRole, getByText encuentran elementos como lo haría un usuario o un lector de pantalla, no dependen de selectores CSS internos.
  • Test end-to-end en un solo it: el primer test cubre el flujo completo del CRUD (agregar → marcar → eliminar), demostrando que todos los componentes se integran correctamente.
  • localStorage.clear() en beforeEach: garantiza el aislamiento entre tests, cumpliendo el principio Isolated.
  • Edge case explícito: el segundo test verifica que el input vacío no genera una tarea, comprobando la validación del formulario.
  • Aserciones expresivas: .toBeInTheDocument(), .toBeChecked(), .not.toBeInTheDocument() de Testing Library son autoexplicativas.
  • Vitest sobre Vite: los tests arrancan casi instantáneamente y se re-ejecutan solo los afectados por cambios, mejorando la experiencia de TDD.

Código del test Código real del proyecto — task.service.spec.ts

describe('TaskService', () => {
    let service: TaskService;

    beforeEach(() => {
        localStorage.clear();
        TestBed.configureTestingModule({});
        service = TestBed.inject(TaskService);
    });

    it('crea una tarea y le asigna un id', () => {
        const task = service.create('Comprar pan');

        expect(task.id).toBeTruthy();
        expect(task.title).toBe('Comprar pan');
        expect(task.completed).toBe(false);
        expect(service.getAll()).toEqual([task]);
    });

    it('devuelve null al actualizar una tarea que no existe', () => {
        const updated = service.update('missing-id', { title: 'x' });
        expect(updated).toBeNull();
    });
});

Elementos técnicos aplicados

  • TestBed es la utilidad de Angular para configurar el módulo de pruebas e inyectar servicios como lo haría el framework en producción.
  • beforeEach asegura que cada test comience con localStorage limpio y un servicio recién inyectado, cumpliendo el principio Isolated.
  • El test "devuelve null al actualizar una tarea que no existe" verifica el comportamiento ante datos inválidos (edge case), un caso frecuentemente olvidado que suele originar bugs en producción.
  • El test "no toca otras tareas al eliminar una" comprueba que la operación DELETE es quirúrgica y no genera efectos colaterales indeseados sobre el resto del estado.
  • Los tests del componente utilizan fixture.detectChanges() para forzar el renderizado del DOM, y simulan interacciones con dispatchEvent y click(), reproduciendo el comportamiento real del usuario.

🏆 Conclusiones

Hallazgos del proyecto

  • El TDD es agnóstico al lenguaje. El ciclo Red → Green → Refactor, la estructura AAA y el principio FIRST se aplicaron de manera consistente en Java, Kotlin, Python, React y Angular.
  • Los frameworks cambian, la filosofía no. @Test en JUnit, it(...) en Jasmine/Vitest y def test_... en pytest son formas distintas de expresar la misma intención: "esta función es un test que debe validarse automáticamente".
  • Los mocks son un patrón universal. Mockito, vi.fn, unittest.mock y jasmine.createSpy resuelven el mismo problema: aislar la clase bajo prueba de sus dependencias.
  • La UI complica pero no cambia el fondo. Probar componentes de React o Angular requiere fixtures, simulación de eventos y verificación del DOM, pero el patrón Arrange-Act-Assert se mantiene intacto.
  • La disciplina TDD produce mejor diseño. Al escribir el test primero, se piensa en la interfaz pública de la clase (cómo se usa) antes que en su implementación (cómo funciona). Esto tiende a producir código más modular y desacoplado.

Conceptos que atraviesan todo el proyecto

Concepto Definición
TDD Metodología en la que se escribe el test antes que el código, siguiendo el ciclo Red → Green → Refactor.
Por qué el test primero Garantiza que el test realmente prueba algo. Un test que nunca ha fallado no es confiable como red de seguridad.
Test unitario vs. integración El unitario prueba una clase aislada; la integración prueba dos o más componentes reales trabajando juntos.
Para qué sirven los mocks Aislar el SUT reemplazando sus dependencias con dobles controlados, para que los fallos apunten al SUT y no a colaboradores.
Principio FIRST Fast, Isolated, Repeatable, Self-validating, Timely: las cinco cualidades de un buen test unitario.
Estructura AAA Arrange, Act, Assert: la organización estándar del cuerpo de cualquier test, en cualquier lenguaje.
